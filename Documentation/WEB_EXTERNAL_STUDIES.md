# Web External Study Integration

Fixed31 adds an External Study launch mode for recruitment/facilitation services such as Prolific, CloudResearch Connect, SONA, and generic URL-based systems.

## Administration

External-study mappings are managed from the existing password-protected Web Settings area:

1. Open **Settings** from the SONAR Startup page.
2. Re-enter the Web operator password once.
3. Choose **External Studies**.
4. Add or edit a mapping.

Settings is now split into separate views: **Experiments**, **Results**, **External Studies**, and **Account**.

Each external-study mapping contains:

- Provider (`Prolific`, `CloudResearch Connect`, `SONA`, or `Generic`)
- Provider Study / Project ID (for SONA this can be a researcher-chosen mapping key)
- SONAR experiment package
- Auto Start
- Show Instructions
- Completion / return URL
- Enabled

Mappings are stored server-side in `/data/config/external-studies.json` (normally the existing Config bind mount). Completion URLs are never accepted from a participant's incoming URL.

## Participant launch flow

A valid external launch does not require the participant to know the SONAR operator password. The server validates the provider study/project mapping and creates a restricted participant session. That session is limited to the assigned SONAR experiment.

The participant ID becomes the normal SONAR `SubjectId`. SONAR also records provider metadata in the run metadata JSON.

### Prolific

Configure the SONAR study link as:

`https://YOUR-SERVER/?provider=prolific`

Configure Prolific to pass URL parameters. SONAR reads:

- `PROLIFIC_PID` -> SONAR Subject ID
- `STUDY_ID` -> external-study mapping key
- `SESSION_ID` -> provider session metadata

The `STUDY_ID` must match **Provider Study / Project ID** in the SONAR External Studies setting.

### CloudResearch Connect

Use:

`https://YOUR-SERVER/?provider=connect`

Configure Connect/the project link so these URL variables reach SONAR:

- `participantId` -> SONAR Subject ID
- `projectId` -> external-study mapping key
- `assignmentId` -> optional assignment metadata

For testing, a URL can be formed as:

`https://YOUR-SERVER/?provider=connect&participantId=TEST&projectId=PROJECT_ID&assignmentId=TEST`

### SONA

SONA replaces `%SURVEY_CODE%` with its participant-specific survey code. Use the launch URL generated by the SONAR External Studies editor, for example:

`https://YOUR-SERVER/?provider=sona&study=SONAR-STUDY-1&subject=%SURVEY_CODE%`

`SONAR-STUDY-1` is the **Provider Study / Project ID** configured in SONAR. The survey code becomes the SONAR Subject ID.

### Generic

A generic integration accepts:

`https://YOUR-SERVER/?provider=generic&study=STUDY_KEY&subject=SUBJECT_ID`

Optional generic parameters are `session`/`sessionId` and `assignment`/`assignmentId`.

## Auto Start and instructions

- **Auto Start = Yes, Show Instructions = Yes**: login/startup/selection are skipped, the assigned experiment is loaded, and the SONAR Instructions view is shown. The participant presses **Start Experiment**.
- **Auto Start = Yes, Show Instructions = No**: the assigned experiment opens directly in the Sonar Task scene.
- **Auto Start = No**: the participant sees the restricted Experiment Selection view containing only the assigned experiment and presses Start manually.

## Completion redirects

SONAR waits for the completed run to be finalized successfully on the server before offering the provider return action. If finalization fails, the participant receives a Retry dialog instead of being redirected with unsaved final state.

When a mapping has a Completion URL, the final **OK** button navigates the current browser tab to that server-configured URL. If no Completion URL is configured, SONAR tells the participant that the results have been saved and that the browser window may be closed.

Provider completion URLs should be copied from the provider's study/project setup. Do not place completion URLs in participant launch query strings.

## Result metadata

`.meta.json` now includes:

- `LaunchMode` (`Standard` or `External`)
- `RecruitmentProvider`
- `ProviderParticipantId`
- `ProviderStudyId`
- `ProviderSessionId`
- `ProviderAssignmentId`

For external sessions the server makes Subject ID, experiment package, and provider metadata authoritative from the authenticated launch session rather than trusting client-submitted metadata.

## Security notes

- External participants do not receive the Settings/admin authorization cookie.
- The normal Web Settings page still requires operator login plus re-authentication.
- External sessions can retrieve only their assigned experiment definition/assets through the SONAR API.
- The server maps provider study/project IDs to experiment packages. Changing `experiment=` in a browser URL does not choose another experiment because experiment package names are not accepted as participant launch authority.
- Provider identity parameters that are not cryptographically signed by the provider can still be manually altered by a participant. The server mapping prevents experiment switching, but it cannot prove that an unsigned participant ID genuinely came from the provider. Signed-provider launch validation can be added as a future hardening option.

## Local WebGL testing

Fixed32 extends **SONAR > Build > Web Local Test (Build and Run)** so Settings and external-study launch URLs can be tested without Docker/API deployment.

1. Run **Web Local Test (Build and Run)**.
2. Log in with the local password `SonarDev123!`.
3. Open **Settings** and re-authenticate with the same password.
4. In **External Studies**, create a mapping to one of the experiments bundled into the local Web build. Local mappings are stored only in browser-local storage.
5. Edit the mapping and copy the generated localhost Launch URL. It contains provider-specific test participant parameters and the selected local experiment.
6. Open that URL in the same local Web server/browser to exercise the external launch path.

Local mode additionally accepts the development-only `experiment=PACKAGE_NAME` query parameter. For example:

`http://localhost:PORT/?provider=generic&subject=TEST01&study=LOCAL&experiment=BasicContactClassification&autostart=1&instructions=1`

`autostart=0|1` and `instructions=0|1` can be used to test the launch branches. Production Web deployments do not use `experiment=` as participant authority.

The other Settings views are also visible locally. Experiments are read-only and come from the project files copied into the Build-and-Run output. Results is visible for layout testing but server result downloads are unavailable. Account is visible but password changes are disabled because the local development password is fixed.

## Existing server upgrade

For an existing fixed30 Web deployment, fixed31 requires:

1. Rebuild and replace the Unity WebBuild from fixed31.
2. Replace `Sonar.Server/Program.cs` with the fixed31 version (or replace the full `Sonar.Server` source directory).
3. Rebuild/recreate the API container.

No Nginx or Docker bind-mount change is required. The existing Config mount will persist `external-studies.json` automatically.
